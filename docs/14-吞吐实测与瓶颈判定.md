# 14 — `throughput.js`：先量清楚"数据到底有没有进来"

> 承接 [13-boost实机验证与瓶颈转移](./13-boost实机验证与瓶颈转移.md)。
> 上一节留下的判断是：**令牌桶已经放开，速度不变 → 瓶颈不在桶里。**
> 但这只是"排除"，还没"确认"。本文的工具用来把另一半补上。

---

## 1. 要回答的问题只有一个

```
配额（桶给的）  vs  真实吞吐（网卡实际收到的）
```

| 情况 | 结论 | 下一步 |
|---|---|---|
| 真实吞吐 ≈ 配额 | 桶确实在限制你 | 继续放开桶（已做） |
| 真实吞吐 ≪ 配额 | **桶给了配额，数据没进来** | 去 netbase / 服务端 |
| 真实吞吐 = 0 | 没在下载，或走的不是 ws2 | 先确认场景 |

---

## 2. 为什么用导出符号，而不是继续找 RVA

上一轮的教训：**地址能猜错，"字节签名唯一匹配"也可能是个死点位。**
导出函数没有这个问题 —— 它们是 PE 导出表里的名字，系统加载器保证地址正确：

| 符号 | 模块 | 拿到什么 |
|---|---|---|
| `WSARecv` / `WSARecvFrom` | `ws2_32.dll` | 收缓冲请求字节 + 同步完成的字节 |
| `WSASend` / `WSASendTo` | `ws2_32.dll` | 发缓冲请求字节 + 同步完成的字节 |
| `WSAGetOverlappedResult` | `ws2_32.dll` | overlapped（异步）完成的字节 |
| `GetQueuedCompletionStatus` | `kernel32.dll` | **IOCP 完成的字节 ← 最接近真实吞吐** |
| `ReadFile` | `kernel32.dll` | 走文件/管道的兜底 |
| `set_rate` / `consume` | `kernel.dll` | 对照组：配额侧（有版本表才挂） |

**一个 RVA 都不猜。** `kernel.dll` 那两个点有 `SizeOfImage` 表就挂，没有就跳过。

---

## 3. 关键设计：异步 I/O 要分开算

网盘这类程序用的是 **overlapped / IOCP**，不是同步 `WSARecv`：

```
WSARecv() → 返回 WSA_IO_PENDING (997)     ← 此时没有收到任何字节
   ...稍后...
GetQueuedCompletionStatus() → 返回字节数   ← 这里才是真实吞吐
```

所以脚本把三者分开统计，不会因为"请求了 64 KiB"就误以为"收到了 64 KiB"：

- `收 · 请求` = 客户端**愿意**收多少（缓冲总长）
- `收 · 完成(同步)` = 同步路径**真的**收到多少
- `IOCP 完成` = 异步路径**真的**收到多少
- `异步占比` = 有多少次走了 pending 路径

**"真实吞吐"取这几者的最大值**，因为不同程序走不同路径。

## 4. 怎么用

```bat
frida -p <baidunetdiskhost 的 pid> -l throughput.js
```

看到 `[+] 开始采样` 后**点一个下载**，等 20~40 秒，然后：

| 命令 | 作用 |
|---|---|
| `report()` | 吞吐对照表 + 结论，**这一段整段发我** |
| `timeline()` | 每个 2 秒窗口一行，看速率抖动和断流 |
| `live()` | 实时滚屏（默认关，开了会刷屏） |
| `stop()` / `start()` | 停 / 继续采样（数据还在） |
| `reset()` | 清零 |

建议**配合 `probe2.js` 一起看**：先跑 `throughput.js` 拿到真实吞吐，
再用 `probe2.js` 的 `boost()` 看桶侧变化，两边对时间轴。

## 6. 三条分支怎么读（对应三种修法）

### A. `收 · 请求` 也很小（比如只有几十 KiB/s）

客户端**根本没有向 socket 要数据**。问题在请求发起侧：
并发连接数、调度频率、或者被 `consume` 抑制。
→ 回到 `probe2.js` 看 `consume` 次数和抽干率。

### B. `收 · 请求` 很大但 `收 · 完成` / `IOCP` 很小

客户端要了，对面不给。这是**网络/服务端侧**的限速，客户端改不了。
→ 这条路走到底就是"换账号/换服务端节点"，代码层面到此为止。

### C. `IOCP` ≈ `收 · 请求` ≈ 桶配额

那就说明桶确实在工作，且带宽被配额卡住。
→ 继续用 `probe2.js` 的 `boost()`（已实测能把桶抬到 524288000）。

## 7. 一个已知的盲区（先说清楚，不装懂）

`GetQueuedCompletionStatus` 是**全局**的 —— 它同时处理下载、上传、心跳、日志等
所有 IOCP 完成。所以：

- `IOCP 完成` 会**偏大**（混进了非下载流量）
- `WSARecv 完成` 只统计同步路径，会**偏小**（网盘主要走异步）

🟡 **两个数都不是纯净的"下载字节数"。** 判断时看趋势和量级，不要当精确值。
要更准就得按 socket 句柄过滤，那需要先拿到下载 socket 的 handle —— 下一步可以做。
