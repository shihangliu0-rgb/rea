# 15 — 92 秒采样说明：PID 28804 根本没在下载

> 承接 [14-吞吐实测与瓶颈判定](./14-吞吐实测与瓶颈判定.md)。
> 用户在 PID 28804 上跑 `throughput.js` 采了 92.3 秒。本文把这组数字算清楚，
> 并对 [13](./13-boost实机验证与瓶颈转移.md) 里"瓶颈在别处"的结论给出**更准确的版本**。

---

## 1. 四个数字，把话说死

用户 `report()` 输出（46 个窗口，92.3 秒）：

```
ws2 收 · 请求        平均 65 B/s    总计 5.9 KiB
ws2 收 · 完成(同步)  平均 0 B/s     总计 0 B
ws2 发 · 完成(同步)  平均 1.0 KiB/s 总计 95.5 KiB
overlapped 完成      平均 0 B/s     总计 0 B
IOCP 完成            平均 2.1 KiB/s 总计 194.7 KiB   调用 18187 次
ReadFile 完成        平均 9 B/s     总计 816 B
异步占比：收 0 次 pending / 发 0 次 pending
```

算一下：

| 项目 | 数值 |
|---|---|
| 若真在下载 120 KiB/s，92 秒应收 | **≈ 11.1 MB** |
| 本进程实际收到的（IOCP 合计） | **194.7 KiB（1.76%）** |
| `WSARecv`/`WSARecvFrom` 请求的缓冲总长 | **6042 B** |
| `WSARecv` 返回 `WSA_IO_PENDING` 的次数 | **0** |
| IOCP 调用频率 | 197 次/秒 |
| IOCP 每次平均字节 | **11.0 B** |

**结论：PID 28804 在 92 秒里一共只"愿意"收 6 KB，一次异步收都没发起过，
平均每次 IOCP 完成只有 11 字节。**
11 字节 / 197 次每秒——这是心跳、保活、协议头，不是文件数据。

→ **28804 不是下载进程（至少这段时间不是）。**
→ 之前 `probe2.js` 在它上面看到的 `consume` 2094 次，是在**空跑限流器**。

这也顺带解释了 `docs/13` 里那句"boost 有效但速度不变"：

> 不是因为"桶放了但数据没来"，
> 而是因为**这个进程本来就没有数据可来**。

🟡 更正：`docs/13` 的措辞把因果关系说得过重了。准确说法是"令牌桶**不是**瓶颈"
这一点仍然成立（桶确实被改大了），但"数据没进来"的原因是**进程选错了**，
不是"服务端不给数据"。

## 2. 这组数据里还藏着一个正面证据

`kernel 对照：set_rate 144 次，平均下发 134.80 MiB/s，最后一次 122880`

- 平均 134.8 MiB/s 是被 `boost()` 当时改的大值拉上去的
- **"最后一次 122880"是 `boost()` 关掉后回落的值**
- `122880 B/s = 120 KiB/s`，**恰好等于 [docs/02](./02-限速机制.md) 里记录的非会员实测值**

而 `docs/13` 的桶表里，`rate = 122880` 的桶只有**一个**：
`0x795b3918`，它的 `consume` 次数（553）在所有桶里最高。

→ **`122880` 这个值就是"非会员限速"在代码里的定量落点**，
  对应的通道就是 `0x795b3918`。这条线索在 `docs/13` 里被"大桶"的说法盖过去了，
  现在明确下来。

⚠ 但要强调：**28804 里这个桶 consume 了 553 次，却一个字节都没出去**。
说明 `TokenBucket::consume(期望字节数)` 是"按**愿意**消费的量扣令牌"，
不是"按实际传输量扣"。所以桶的 consume 次数本身**不能**当作"在下载"的证据。
（这一点也修正了 `docs/02` 里"consume 不通过就不发 request"的表述：
它说的是"请求被抑制"，不是"数据被限制"。）

## 3. 还有一个可能：文件根本不是走 TCP 收的

`WSARecv` 请求 6 KB、`overlapped` 0、`ReadFile` 816 B，而 `IOCP` 有 18 万次调用。
这种组合还有另一种解释：**这个进程的文件数据根本不走 `ws2_32`**。

可能性（按概率）：

1. **下载在别的进程**（最可能，见上）
2. 这个进程是"控制面"，数据面在 `BaiduNetdiskHost.exe` 或 YunDls 相关进程
3. 用了自己实现的网络栈（netbase.dll 直接 syscall / 自带 socket 封装）——
   如果这样，`ws2_32!WSARecv` 就挂不到它，得换 `ntdll!NtDeviceIoControlFile` 之类
4. 数据走内存映射/共享内存（P2P 分片落地）

第 3、4 条要靠下一轮数据排除，**现在不下结论**。

## 4. 新工具：`active_pids.py`（多进程同时采样）

```bat
python active_pids.py --seconds 20
```

它同时 attach 所有百度相关进程（`baidu/netdisk/yun/bd/p2p/dls` 关键词），
每个进程挂同样的三个导出函数（`WSARecv` / `WSARecvFrom` / `GetQueuedCompletionStatus`），
**一个 RVA 都不猜**，按 2 秒窗口出排行：

```
  t(s)     pid/name                收(请求)        IOCP     IOCP次数
  ----------------------------------------------------------------------
  2.0      28804 BaiduNetdisk         0.0K         2.0K         380
  2.0      6120 BaiduNetdiskHost    118.5K       118.9K        1204     ← 这个才是
...
★ 下载最可能在：pid=6120  BaiduNetdiskHost.exe
  → 把探针挂到它上面：
      frida -p 6120 -l throughput.js
      frida -p 6120 -l probe2.js
```

如果所有进程吞吐都 < 100 KiB，它会直接说：

```
  但有吞吐的进程太小（< 100 KiB）—— 说明这段时间根本没有下载在跑。
  请确认：① 下载任务真的在走 ② 采样期间确实在传输 ③ 不是别的用户会话
```

参数：

| 参数 | 说明 |
|---|---|
| `--seconds 20` | 采样时长（默认 15） |
| `--window 2000` | 窗口毫秒（默认 2000） |
| `--all` | 连非百度进程也扫（临时排除"是不是别的进程在下载"） |
| `--pid 28804 6120` | 只测指定 pid |

## 5. 下一步（按顺序）

1. **跑 `active_pids.py`**，找出真正在收字节的 pid
   - 找到 → 把 `throughput.js` 挂过去，重做一次"配额 vs 吞吐"对照
   - 全都很小 → 说明采样期间没有下载，先把下载跑起来再采
2. 如果目标 pid 上 `ws2_32!WSARecv` 依然 0 字节，但速度确实有 120 KiB/s
   → 走的是非 `ws2_32` 路径，改挂 `ntdll!NtDeviceIoControlFile`
3. 拿到"真实吞吐 ≈ 120 KiB/s"和"某桶 rate = 122880"同时成立的那次采样
   → 才能确认 `0x795b3918` 这一路就是限速通道
