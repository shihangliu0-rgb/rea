# 11 — 242 版限速点位复核：为什么 10 个 hook 零命中，以及现在该怎么查

> 本文是对 [10-242版本重定位](./10-242版本重定位.md) 的**纠错**。
> 10 号文档的 12 个点位在"字节签名唯一匹配"这一层是对的，但当时把它写成了
> "点位已验证可用"——这是错的。用户真机 `stats()` 实测推翻了它。

---

## 1. 实测证据（决定性，优先于任何静态推断）

用户机器 `frida -p 28804 -l hooks.js` 跑完，REPL 敲 `stats()`：

```
---------- hook 命中统计（累计 2873 次）----------
  bucket.set_rate : 208
  bucket.consume : 2665
  从未被调用：set_param, update_max_speed, set_restrict_ratio, calculate_target_speed,
  cdn_speed_limit_dispatch, close_cdn(decided), set_try_speedup_flag, block_gate(pre),
  download_threshold, set_download_restrict_ratio
```

同时下载日志里速率被压在：

```
rate=16384 cap=16384            ← 0x4000，set_rate 的地板值
rate=1006860 cap=1006860
rate=104857600 cap=1006860
rate=104857600 cap=104857600
```

结论：**12 个点位里只有 2 个在活的调用链上。**

---

## 2. 纠错：我之前说错的两句话

| 之前说的 | 实际情况 |
|---|---|
| "12 个点位已重定位并验证" | 只验证了"这 12 处字节在文件里能唯一定位"，**没有**验证运行时会执行 |
| "`set_rate` 里的 `0x4000` 是限速地板" | 这半句仍然成立，但要补一句：**大部分 set_rate 调用根本不是限速，是构造期初始化** |

## 3. 静态复核：把 12 个点位分成两类

`re/tools/audit_points.py` 可以复跑，输出如下（样本 `bin/kernel.dll`，
`SizeOfImage=0x2b25000`，12 个点位前 32 字节与用户机器逐一比对通过）：

```
点位                           RVA       位置        E8调用  取地址  运行时命中
set_param                    0x125f20  函数入口      2      0      未测
update_max_speed             0x2e7e70  函数入口      1      0      未测
set_restrict_ratio           0x2e7a50  函数入口      0      0      未测
calculate_target_speed       0x2e8800  函数入口      2      0      未测
bucket.set_rate              0xdd320   函数入口      43     0      208 次
bucket.consume               0xdd340   函数内部      0*     0      2665 次
cdn_speed_limit_dispatch     0x2f83ae  函数入口      0      0      未测
close_cdn(decided)           0x1b25bd  函数内部      0*     0      未测
set_try_speedup_flag         0xe52c0   函数入口      0      0      未测
block_gate(pre)              0x1b3788  函数内部      0*     0      未测
download_threshold           0x1b3a03  函数内部      0*     0      未测
set_download_restrict_ratio  0x28a0f0  函数入口      0      0      未测
```

关键区分（这条搞混过一次，别再混）：

- **`函数内部` + E8 调用数 0** 是**废话**。探针落在别人函数中间，当然没人"调用"这个地址。
  这些点位的存活只能靠运行时命中证明，而实测它们是 0 —— 所以**地址本身可能没错，是探针落点选错了**。
- **`函数入口` + E8 调用数 0** 才是真的可疑（候选死代码）。
- **`set_param` 是导出函数**（导出表里名字就叫 `set_param`，RVA `0x125f20`）。
  它零命中不是地址错，而是**说明下载任务根本没走 `set_param` 这条 API 路线**。
  这对定位很有价值：网盘主程序用的是别的入口。

### 3.1 `bucket.consume` 的真相

`0xdd340` 其实是 `set_rate` 函数体内的一条指令地址，不是独立函数：

```
0xdd320  mov eax,[esp+4]        ← set_rate 真正入口（ret 4 收尾）
0xdd324  test eax,eax
0xdd326  je 0xdd33b
0xdd328  mov [ecx+0x20],eax     ← rate 写进 +0x20
0xdd32b  cmp eax,0x4000
0xdd330  mov edx,0x4000
0xdd335  cmova edx,eax          ← cap = max(rate, 0x4000) 写进 +8
0xdd338  mov [ecx+8],edx
0xdd33b  ret 4
0xdd340  push ebx               ← "consume" 从这条开始
```

`0xdd340` 与 `set_rate` 之间**没有 `int3` 填充**，只能靠 `set_rate` 末尾的 `ret 4`
机器码 `c2 04 00` 当边界。它跑得通（2665 次），说明 Frida 在这条指令上插跳板没崩，
但**它到底是不是虚表里的 `consume` 槽位，没有验证过**。
`0xdd340` 处读 `+0x20`(rate)、`+8`(cap) 是安全的：`set_rate` 刚写过这两个偏移。

### 3.2 `set_rate` 的 43 个直接调用者：绝大多数是构造期初始化

| 压栈的立即数 | 次数 | 含义 |
|---|---|---|
| `0x80000` | 11 | 512 KiB/s，构造函数里给各通道的初始速率 |
| `0x1F400000` | 7 | 哨兵=不限速 |
| `0x6400000` | 2 | 100 MiB/s |
| `eax/edx/edi/esi` | 8 | 动态值（`calculate_target_speed` 那条路走这里） |
| 未识别 | 11 | 需要更宽的反汇编窗口 |

代表样例：

```
0xe32c0: push 0x80000 ; call set_rate   ×8      ← 构造期初始化，跟限速无关
0xe52c0 / 0xe5640: push 0x1F400000 ; call set_rate  ← 直接给不限速
0x2e82c7: push eax ; call set_rate      ← calculate_target_speed 的目标值落地点
0x19fcec / 0x19fd4c: push [..+0xa8/0xac/0xb0] ; call set_rate  ← 配置里的三个限速档位
```

四个 `push eax` 里最重要的是 **`0x2e82c7`**：它在 `0x2e813a` 函数体内，
而 `0x2e813a` 正是调用 `calculate_target_speed`（`0x2e8800`）的那两个函数之一。

> 静态能看到的就到这。**真正把速率压到 16384 的是哪条路径，静态图看不到**——
> 因为 `calculate_target_speed` 返回的是"本 tick 目标"，而 16384 是 `set_rate`
> 在**上游给 ≤16384 时**打的地板，上游那一步是虚调用/函数指针，没有 E8 可追。
> 所以下一步必须用运行时调用栈，不能继续猜地址。

## 4. 下一步：`probe2.js`（一次运行拿全证据）

`re/frida/probe2.js` 只 hook 两个已知活着的点，不猜任何新地址，记录
**完整调用链 + 线程 + 每个令牌桶的 rate/cap**，并且能按速率反查。

```
frida -p <baidunetdiskhost 的 pid> -l probe2.js
（点一个下载，等 10~30 秒）
```

| 命令 | 作用 |
|---|---|
| `report()` | 总览：速率分布 / 调用者排行 / **谁把速率设成 16384** / 令牌桶表 / 一行可粘贴摘要 |
| `why(16384)` | 只打印"下发 16384"的完整调用链，按链去重计数 |
| `chains()` | 原始样本，带时间序、线程号 |
| `buckets()` | 当前所有令牌桶的 rate/cap |
| `reset()` | 清零 |
| `boost()` | **强制提速开关**（唯一写内存的入口，见下） |

`report()` 第 5 节会输出类似：

```
set_rate callers: 0x2e82c7=143, 0xe32f9=8, ...
set_rate rates  : 16384x5, 1006860x2, 104857600x6
consume callers : 0xdd1e0=2665
buckets         : 0x1234abcd(rate=16384,cap=16384,n=2665)
```

**这几行整段发我，不用截图。** 有了 `0x2e82c7` 的调用链，就能定位到
"谁算出 16384"的那一层。

### 4.1 `boost()` —— 唯一会写内存的东西

默认关闭，脚本纯观察。敲 `boost()` 后：

1. `set_rate` 的入参直接换成 `0x1F400000`（524288000 B/s）
2. 每次 `consume` 之前，把桶的 `+0x20`(rate)、`+8`(cap) 再写一遍

它**不会重新 attach**（重新 attach 就是之前踩过的 `e9` 跳板坑：
签名会读出 `实际=e9 bf 44 5e 8d`，那是 Frida 自己的跳板）。

`boost()` 的效果**尚未在真机上验证**。而且它只解决"桶里 rate=16384"这一层：

- 如果 `boost()` 后速度上去了 → 瓶颈就是令牌桶，收工。
- 如果 `boost()` 后 rate 已经是 524288000 但速度不变、且 `consume` 次数也不变
  → 瓶颈在"每 tick 只发 N 个请求"（consume 的调用频率），不在令牌桶。
  那时 `report()` 里 `consume 共 X 次` 这个数字就是下一个要攻的目标。

## 6. 本轮仍未解决

- ⚪ **谁算出 16384** —— 等 `report()` / `why(16384)` 的输出。
- ⚪ **`boost()` 是否真能提速** —— 未上真机。
- ⚪ 那 10 个死点位（用户要求全部重新定位）—— **本轮只完成了静态审计，
  还没给出新地址**。理由写在前面：没有运行时调用栈就换地址，等于再猜一次，
  而"猜地址"正是上一版翻车的原因。用 `probe2.js` 拿到调用链后，
  新地址应当从调用链里长出来，而不是从字节签名里搜出来。
