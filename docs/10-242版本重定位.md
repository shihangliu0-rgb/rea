# 10 · 3.0.20.242 内核重定位（12 个点位全量）

> ⚠️ **本文的 12 个点位只保证"字节在文件里唯一匹配"，不保证"运行时会执行"。**
> 用户真机 `stats()` 实测：只有 `bucket.set_rate`(208) / `bucket.consume`(2665) 命中，
> 其余 10 个全部 0 次。复核过程与下一步见 [11-242点位复核与调用栈追踪](11-242点位复核与调用栈追踪.md)。

> 结论先行：**同一个客户端 8.1.6.101 会带不同版本的 `kernel.dll`**（内核静默热更新）。
> 原先的 12 个 RVA 是 3.0.20.237 的；实测机器上是 **3.0.20.242**，
> 现已在新版本上全部重新定位并交叉验证，`hooks.js` 内置两张表、按模块大小自动选择。

## 1. 两版对照

| 项 | 3.0.20.237（旧样本） | 3.0.20.242（实测机器） |
|---|---|---|
| 文件大小 | 44,170,496 | **45,129,984** |
| `SizeOfImage` | 0x2a3a000（42.23 MB） | **0x2b25000（43.14 MB）** |
| `TimeDateStamp` | 1788347401 | **1790047935** |
| `.text` | 0x1000–0x1185527 | 0x1000–0x12520a7 |
| `BaiduNetdisk.exe` | 8.1.6.101 | **8.1.6.101（没变）** |
| `YunDls.dll` / `YunLogic.dll` | 8.1.6.101 | **8.1.6.101（没变）** |
| `BaiduNetdiskHost.exe` | 旧样本中没有 | **7.57.0.102（新增）** |

**关键**：客户端三个主要模块版本号完全一致，只有内核换了。
所以按"客户端版本号"判断内核版本是**不可靠的** —— 必须看 `kernel.dll` 自己的 `SizeOfImage`。

### Δ 不均匀，不能统一平移

- `.data` / `.rdata` 附近 Δ 小（`set_param` +0x3930、`set_try_speedup_flag` +0x2310）
- 中段 Δ 中等（三个 `+0x3a50`）
- 大函数区 Δ 最大（`+0xac70`、`+0xa210`）

早期我曾按 +0x3a50 去推 `download_threshold`，碰巧对了 —— 但这是**运气，不可推广**。

## 3. 三重交叉验证

单靠字节锚点容易选错。242 的点位由三条独立路径互相印证。

### 3.1 vtable 确认 `bucket`

```text
237  @0x118cb44 = [0x10004c70, 0x100db150, 0x100db090, 0x100db170]
242  @0x1259b24 = [0x10004c70, 0x100dd320, 0x100dd260, 0x100dd340]
                     ↑ctor        ↑set_rate(+4)  ↑dtor        ↑consume(+12)
```

`0x100dd320` 在整个 43MB 里**只出现这一次**（就是 vtable 槽位），
槽位语义与 237 一一对应。

### 3.2 布局约束确认 `calculate_target_speed`

```text
237: 0x2ddb90 − 0x2dd200 = 0x990
242: 0x2e8800 − 0x2e7e70 = 0x990   ✓
```

同一类的相邻成员，编译器重排概率极低。

### 3.3 调用关系确认 `set_try_speedup_flag`

242 的 `0xe52c0` 内部调用 `set_rate`（0xdd320）**6 次**：

```text
0x0e53f9  0x0e5405  0x0e5445  0x0e544d  0x0e564b  0x0e565b
```

与 `docs/07` 描述的"置位时对 4 组令牌桶调 `set_rate(0x1F400000)`"吻合。

### 3.4 桶语义不变（这是最硬的证据）

```text
set_rate @0x0dd320                      (237 @0xdb150 完全相同)
  mov eax, [esp+4]      ; rate
  test eax, eax
  je  +0x15             ; rate==0 直接返回
  mov [ecx+0x20], eax   ; 存 rate
  cmp eax, 0x4000
  mov edx, 0x4000
  cmova edx, eax        ; max(rate, 0x4000)
  mov [ecx+8], edx
  ret 4

consume @0x0dd340                       (237 @0xdb170 完全相同)
  push ebx/edi/esi ; mov esi,ecx
  mov edi,[ecx+0x18] ; mov ebx,[ecx+0x1c]   ; 上次时间戳
  call 0x100d17d0                            ; 取当前时间
  ...
```

字段偏移 `+8 / +0x18 / +0x1c / +0x20` 与 `docs/02` 记录的结构体布局一致。

### 3.5 逐条反汇编比对

12 个点位在两版上反汇编前 10 条指令，**归一化绝对地址后 11/12 完全相同**：

- 5 个最初显示"不一致"的点，全部只是**相对跳转目标**和**绝对数据地址**随代码移动而变化
  （如 `mulsd xmm1,[0x1119b798]` → `[0x11268778]`），属预期
- 唯一真实差异：`set_try_speedup_flag` 把 `esi` 换成 `edi`，不影响 hook

## 4. `hooks.js` 现在的用法

不用手改 RVA，**按模块大小自动选表**：

```js
var PROFILE = 'auto';
```

启动输出：

```
[+] 版本核对通过：SizeOfImage = 0x2b25000 (43.14MB)
[i] 使用 RVA 表: 3.0.20.242（SizeOfImage=0x2b25000 (43.14MB)，内核热更新版）
========== 安装完成：成功 12 个，跳过 0 个 ==========
```

遇到第三张表：

```
[!] 没有匹配 SizeOfImage=0x2c1d000 的 RVA 表
    内置表：3.0.20.237=0x2a3a000, 3.0.20.242=0x2b25000
    用 rescan.py 生成新表后加进 PROFILES，或手动设 PROFILE
```

## 6. 换任何新版本的复现流程

1. `python rescan.py --dll "<新 kernel.dll>"`
   —— 32~56 字节通配锚点，**只在参考文件唯一命中时才认作有效锚点**
   （短签名排序不可信，这点已踩过坑）
2. 多候选/未命中的点位，按此顺序换锚点：
   - **vtable 槽位**（最可靠，语义明确）
   - **相邻函数的固定相对距离**（同类的相邻成员）
   - **调用关系**（A 内部调用了已确认的 B）
   - 长字节锚点（≥48 字节，要求参考侧唯一）
3. `python verify_rva.py --profile` 校验，然后加进 `hooks.js` 的 `PROFILES`
