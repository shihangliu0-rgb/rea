# 06 · 变速工具为什么"开始有效、后段反噬"

> 针对的现象：开变速 → 能跑到 ≈1 MB/s；下载到后段（或跑久了）→ 变速越大越慢，掉到几十 KB/s；
> **把变速关掉反而回到 ≈100 KB/s**。
>
> 本文所有地址都是 `kernel.dll` 的 **RVA**（基址 `0x10000000`）。
> 这一篇是**推断性最强的一篇**：结论来自代码路径 + 数值关系 + 服务端上报字段的交叉印证，
> 用 ✅/🟡/⚪ 标注；能落到"某条指令"的地方都是实测反汇编。

---

## 0. 一句话结论

**你调大的那个"速度"，同时被当成了"这轮该下多少"的分母。**

客户端里有两个东西共用"限速器算出来的那个速率"（`0x2ddb90` 的返回值，存在 `[edi+0xBC]`）：

| 用途 | 位置 | 语义 |
|---|---|---|
| ① 令牌桶 rate | `set_rate` @`0xdb150` | 每秒允许多少字节 → 这是"变速工具"改的东西 |
| ② **这段窗口内"应该完成多少"的门限** | `[edi+0xBC]` 直接读、再 `×0.8 / ×1.3` | 达不到就算"慢"，进入惩罚分支 |

于是：

- 前段：剩余数据多，"应该完成量"总能满足 → 门限不触发 → 你把 rate 调大 → **变快**（✅ 与观察一致）
- 后段：剩余数据少，但**门限还是按你调大的 rate 算出来的**（还剩多少块 ≤ rate/3 就开始卡）
  → 门限一直不满足 → 进入"慢"分支（`0x1affcb`，日志 `task_download_rate=…|download_threshold_speed=…`）
  → 降并发 / 关 CDN / 压 `restrict_ratio` → **掉到几十 KB/s**
- 这时候你把变速关掉：rate 变小 → **门限也变小** → 门限变得容易满足 → 各项惩罚撤掉
  → 速率回到会员默认档 ≈ **100~120 KB/s**（✅ 与观察到的"关掉反而涨到 100KB 左右"完全吻合）

## 1. 关键代码：门限 = 速率 × 0.8 / × 1.3

函数 `0x1afb70`（选择"下一个要下的块"，含 `select this,slide_start=…` 日志逻辑）。
它在 `0x1afeed` 之后做了一次**"该不该继续放开"的判定**：

```asm
; 0x1afeed —— 取"限速器算出来的速率"
mov  ecx,[ebp+8]            ; 上下文
mov  ecx,[ecx+0x10]
mov  eax,[ecx]
mov  eax,[eax+0x30]         ; vtable[12]
call eax                    ; → eax = float task_download_rate
mov  [esi+0xc],eax

mov  ecx,[ebp+8]            ; 同一对象
mov  ecx,[ecx+0x10]
mov  eax,[ecx]
call dword ptr [eax+0x74]   ; vtable[29]
mov  ecx,eax
call 0xdb010             ; ★ getter: return *(this+8)  ← 令牌桶的 capacity（= rate）
mov  [esi+0xbc],eax         ; ← 这个值就是日志里的 download_threshold_speed

; 换算 double：qword[0x1118d070] = 2^52（int→double 惯用法）
mulsd xmm2,[0x1119b750]     ; 0.8
ucomisd xmm2,xmm0
jbe  0x1affb3               ; ← 0.8 × threshold > task_rate ? 继续放 : 走"慢"分支
...
0x1affb3: mulsd xmm1,[0x1119b798]   ; × 1.3
          ucomisd xmm0,xmm1
          jbe   0x1b0321            ; ← task_rate ≤ 1.3 × threshold ? 放行

0x1affcb: 打日志 0x11283d33 = "task_download_rate=%1%|download_threshold_speed=%2%"
          → 进入限制分支（不再选新块 / 收紧）
```

**两个常量实测**（在 `.rdata` 里按 8 字节 IEEE754 取）：

| 地址 | 值 |
|---|---|
| `0x1118d070` | 4503599627370496.0 = `2^52`（int→double 修正项，不是数值） |
| `0x1119b750` | **0.8** |
| `0x1119b798` | **1.3** |
| `0x1119b770 / b778 / b780 / b788` | 9.0 / 0.25 / 1024.0 / 2^31（`close cdn` 用的那组） |

而 `0xdb010` 本身只有三条指令，是**令牌桶容量 getter**：

```asm
mov eax,[ecx+8]
ret
```

>`AccumulateTokenBucket` 的布局（`0xdb020` 构造函数）：
>`+8 = capacity`、`+0x10/0x14 = 当前令牌（64 位）`、`+0x20 = rate`、`+0x24 = 1000`(时间基)、`+0x1C/0x18 = 上次 QPC`。
>**注意 `set_rate` 里 `[+8] = max(rate, 0x4000)`** —— 所以"容量"永远跟着 rate 走（✅ `0xdb150` 实测）。
>这就是"**你调大 rate，门限跟着一起变大**"的物理原因。

## 2. 为什么"偏偏是快下完的时候"

### 2.1 门限是不变的，剩余量在变少 ✅

门限 `threshold` 只跟 rate 有关，**跟剩余多少没关系**。而"这一窗口能完成的量"跟剩余量成正比。
块大小 `donwload_file_downloading_file_block_size = 524288`（512 KiB），
单次 HTTP range 上限 `donwload_file_max_httprange_size = 4194304`（4 MiB）。

设变速把 rate 调到 `R`（比如 8 MB/s），则阈值 `T = R`（≈8 MB/s = 8 MiB/s）。
剩 4 MiB 数据时，最理想情况下一轮全下完，**瞬间速率也就约 4 MiB/s < 8 MiB/s → 判"慢"**。
也就是说：

> **只要剩余数据 < T × (判定窗口)，就必然判"慢"；此时无论怎么加变速，都只会让 T 更大、更容易判慢。**

按 1 秒窗口 + `T = R` 粗算，"必判慢"的水位线是 `剩余 ≤ R`。R 调成 8 MiB/s 时，最后 8 MiB 都在这个坑里。
反向验证：**关掉变速**时 R 回到会员默认（写死 `max_speed` ≈ 400 KiB/s 档），水位线降到几百 KB，
于是"最后一点"又重新满足了门限，惩罚撤掉，速度回到 ≈**100~120 KiB/s**。

> 🟡 判定窗口的具体时长没在静态里定死（`0x1afb70` 的 `[esi+0xE4]` 是"速率"、`[esi+0xE0]` 是"比值"，
> 另有 `cmp eax,0xb / jb` 这类**剩余块数 ≤ 11 就不再请求**的小阈值）。但**"门限∝rate、剩余∝时间"** 这个
> 结构足以解释"后段反噬、关掉反升"。

### 2.2 最后一段的并发本来就少 ✅

`0x1b1030 choose_http_peer_to_connect_for_one_task` 的调用点紧挨着一个日志：

```
connect_ct=%1%|small_file_connect_cnt=%2%|task_handle=%3%|remaining_block_ct=%4%|need_cnt=%5%
```

`remaining_block_ct` / `need_cnt` 说明**连接数是按"还剩多少块"算的**。
剩 1~2 块时能并发的链路只有 1~2 条，跟第 1 点叠加，后段天然更慢。

### 2.3 收尾还会"主动关连接" ✅

`force_close|blocks=%1%|surplus_piece=%2%|req_avg_speed=%3%|handle_id=%4%|pid=%5%|...`（`0x127376e`）
——收尾时会把"没及时返回 piece"的连接按 `req_avg_speed` 排一下直接 force close。
`choose_slow_http_peer_for_close` @`0x1a609f` 是同一套思路：**挑最慢的关**。

### 2.4 块请求有"超额"惩罚 ✅

`exceed max block request interval`（`0x124aba0`，xref `0xd66e8d`）——请求块太密/太久不完成会被判超额。
你调大 rate 后一次要的块变多，更容易踩到。

### 2.5 磁盘写入在后段才是瓶颈 ✅

`disk_slow_check`（`0x24c4b4`）读三个配置：

```
business/disk_slow_check                     = 1
business/block_left_count                     = 125
business/large_non_ntfs_file_size_threshold   = ?
日志: disk_slow_check=%1%|block_left_count=%2%|large_non_ntfs_size_threshold=%3%
```

写盘按 `download_file_write_disk_once_size = 262144`（256 KiB）一次。
**rate 调高 = 单位时间涌入的块变多 = 写盘队列变长**，一旦超过 `block_left_count` 阈值就判"磁盘慢"，
而"磁盘慢"的处置同样是**降速**（这是 CDN 之外另一个独立降速阀）。

### 2.6 服务端也在看你怎么用 ✅（这条能解释"开了变速后整体掉档"）

上报串（`0x2f667e` `report_download_common`）里有一整排专门给"变速/限速"用的字段：

```
…@#total_speed_limit=%8%:%9%@#cdn_speed_limit=%10%:%11%@#current_speed=%12%
 @#sample_avg_speed=%14%@#sample_max_speed=%15%@#p2p_bandwith=%16%@#p2s_bandwith=%17%
 @#cur_task_tail_time=%24%            ← ★ "尾部耗时"
 @#less_100k_ct=%94% @#between_100k_500k_ct=%95% @#between_500k_1M_ct=%96%
 @#between_1M_4M_ct=%97% @#between_4M_20M_ct=%98% @#more_20M_ct=%99%
```

`sample_max_speed` 会把你"瞬时冲上去"的速率原样上报，而 `less_100k_ct / between_100k_500k_ct`
是**低速次数直方图**。后段你因为 2.1 被压到几十 KB/s，就会不停往 `less_100k_ct` 里加分。
下一轮 `p2p_switch_param` 依据这些统计调整 → 这就解释了"**用久了整体变慢，重启/换号才恢复**"。🟡

## 3. 还有两个"越调越慢"的纯客户端机制

### 3.1 每连接一个令牌桶，桶多不等于快 ✅

`0x100b08f0` 这个构造函数里连续创建了十几个桶（`+0x6b0, +0x6e0, +0x710, …` 每 0x30 一个，
外加 `+0x250/0x2a0/…/0x660` 共 14 个 `0x100b03e0`），说明**限速器是按连接/按通道分桶**的。
总带宽 ≈ **有效连接数 × 每桶 rate**。变速工具通常只改"总速率"这一个数字，连接数侧的上限
（`download_datablock_channel_count_max = 30`、`connect_count_for_normal_level1/2/3 = 4/2/1`）没变
→ 于是"rate 很大但拉不到数据"，反而更容易触发第 1 节的门限判定。

### 3.2 `close cdn` 的阈值是 1~2 MiB/s，不是 120 KB/s ✅

`0x1aea38`（核心 `0x1aeadc`）里 `cdn_speed = (9−level)×0.25 MiB/s`（2/1.75/1.5/1.25/1.0 MiB/s），
`base = 0x20 − level*4`（28/24/20/16/12）。判定是"实测速度 < level×base 或 速率 < cdn_speed → 关 CDN"。

**关键点：这个阈值是按"正常应该有多快"设的。** 你前段靠变速冲到 8 MB/s 时它不触发；
后段一掉下来（因为第 1 节），它开始触发 → 关 CDN/onecloud → 只剩 P2P → 更慢。
日志 `don't close cdn|…|remaining_block=%8%`（`0x112717b6`，xref `0x1afdef`）也证明这条判定
**把 `remaining_block` 当输入**：越接近收尾越容易走到"关"这一侧。✅

## 4. 把现象和机制一一对应

| 你观察到的 | 代码里的原因 | 等级 |
|---|---|---|
| 开变速 → ≈1 MB/s | 令牌桶 rate 被抬高，`consume()` 放行更多 request | ✅ |
| 后段掉到几十 KB/s | 门限 `T ∝ rate`（`0x1affb3`，×1.3/×0.8）；剩余量 < T 就必判慢 | ✅ 结构 / 🟡 窗口 |
| 变速开得越大越慢 | T 随 rate 线性变大 → 越容易判慢；同时 `exceed max block request interval`、`disk_slow_check` 更容易踩 | ✅ |
| 关掉变速反而回到 ≈100 KB/s | rate 回落 → T 回落 → 惩罚撤除；且 base 速率回到会员档 100~120 KB/s | ✅ |
| "下载久了也变慢" | 低速次数直方图（`less_100k_ct`）等上报 → 服务端下一轮压参数 | 🟡 |
| 最后一点点特别慢 | `remaining_block_ct` 决定连接数；`force_close|surplus_piece`；剩余块 ≤11 不再请求 | ✅ |

## 5. 你可以自己验证（不用改任何东西）

```bash
frida -f "…\BaiduNetdisk.exe" -l re/frida/hooks.js
```

第 9/10 组 hook 会打印：

```
[gate] left_block=… rate=… ratio=…            ← 剩余块数 vs 速率
[threshold] download_threshold_speed=… B/s    ← 门限（= 桶容量 = rate）
[ratio] new=…%                                ← restrict_ratio 被谁改
```

**看这三行就能确认**：下载到后段时 `rate` 仍然是变速后的大值，而 `left_block` 在逼近 0，
`threshold` 一直等于 `rate` —— 门限恒大于"还能下的量"，于是永远判慢。把变速关掉，`threshold` 立刻掉到
几十万，判定恢复。这就是"关掉反而变快"的直接证据。

## 6. 结论与推论（诚实标注）

1. **变速工具的收益只在前段成立**：它抬高的是"每秒允许"的上限，不是"每秒能拿到"的供给。
   到了尾巴，供给（剩余数据 + 并发链路）本来就少，上限再高也没用。✅
2. **更大的变速值会让"慢"的判定更容易成立**，因为门限是拿 rate 当标尺的。这是"越大越慢"的核心。✅
3. **关掉变速能回血**，是因为把标尺同时调小了，而不是因为"关掉会让服务端给你更多带宽"。✅（这一点很重要：
   说明后段的瓶颈主要是**客户端的自我判定**，不是服务端）。
4. 服务端侧（上报 → 下一轮参数）是否也在参与，无法从静态证明，**本仓库没有抓包**。⚪
5. 如果目的是"稳定而不是峰值"，正确的做法不是把 rate 调到很大，而是**让 rate 贴近链路实际能力**
   （例如按 1~2 MB/s 设），这样门限始终可满足，反而不容易触发后段惩罚。这是从代码结构推出来的，
   **未做对照实验**。🟡
