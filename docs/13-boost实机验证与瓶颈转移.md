# 13 — boost() 实机验证结果：令牌桶已经不是瓶颈了

> 承接 [12-限速决策器定位](./12-限速决策器定位.md)。
> 本文基于用户 2026-11 在 PID 28804 上跑的**两轮 report() + boost()** 实测数据。
> 结论方向变了：**原来假设"令牌桶是限速点"这一条，在用户的账号状态下不成立。**

---

## 1. boost() 到底生效了没有？—— 生效了，而且很明显

用户敲 `boost()` 之后再点下载，`report()` 显示：

```
[BOOST 打开] 已改写限速器 196 次，set_rate 入参 333 次，重写桶 2663 次
set_rate rates : 524288000x338, 16384x85, 122880x20, 1006860x19, 104857600x11
```

| 指标 | boost 前 | boost 后 | 判定 |
|---|---|---|---|
| `set_rate` 入参分布 | 16384 占 **54.5%** | 16384 掉到 **18.0%**，524288000 涨到 **71.5%** | ✅ 改写生效 |
| 主桶 `0x795b3918` 的 rate | 122880 | **524288000** | ✅ 生效 |
| 主桶 consume 次数 | 553 | **1853** | ✅ 请求频次 ×3.3 |
| 桶总数 | 19 → 61 → 67（持续新建） | — | 说明线程/连接在不断增加 |

**所以：`+0x20`(rate) / `+8`(cap) 这两个偏移是对的，`+0xb0` 也是对的。**
上一版标 🟡 的那一层，现在可以升为 ✅。

---

## 2. 但是速度没变 —— 这是本轮最重要的结论

> 用户原话："现在没有反应还是正常的速度"。

`boost()` 已经把**能被改的都改了**：

- 限速器的 `+0xb0`（限速值）→ 524288000
- `set_rate` 的全部入参 → 524288000
- 每个桶的 rate / cap → 524288000（2663 次重写）

**令牌桶这一层已经彻底放开，速度仍然不变。**
→ **限速桶不是当前的瓶颈。** `docs/02` 里"卡带宽的动作是 `TokenBucket::consume`"这一条，
在**"账号本身被限到 120 KiB/s"的场景下成立**；在**用户当前账号状态（限速器 -1）下不成立**。

---

## 3. 上一版两个读错的字段（已修）

用户第一份 `report()` 里出现了：

```
开关状态：开 0 个 / 关 0 个
0x8221c78  限流值(+0xb0)=104857600   开关(+0xb4)=4294967295
```

**`4294967295` = `-1`（有符号）= 不限流。** 我上一版按 `readU32` 读，判成"既不开也不关"，
于是给了一个错误结论："开关是关的，16384 是构造默认值，真正压速度的是那些大桶"。

现已改为 `readS32`，判读逻辑重写：

```
0x8221c78  限流值(+0xb0)=104857600   开关(+0xb4)=-1
判读：5 个限速器 = -1（不限流），0 个真在限流；桶里 21 个已是大速率，5 个还在地板。
```

顺带一个观察：`+0xb0 = 104857600`（100 MiB/s）即使限速器开启也不构成限制，
真正会卡人的是 `+0xb0` 很小的那种对象。用户机器上**一个都没有**。

---

## 4. 结构补全：`0x19fab0` 是模板基类，不是单一限速器

用户三次 `report()` 里限速器对象数：5 → 19 → 21，`+0xb8` 全是 `120`，
`set_enabled` 的调用者全是 `0x23e09a`。静态上 `0x19fab0` 被**5 个 vtable** 引用
（`docs/12` 里已知"签名唯一匹配 2 次"，其余是字节相似，需再核）。

合理解释（🟡 推断，未证实）：这是**每连接/每通道一个**的限速器基类，
`+0x78` 内嵌 TokenBucket（这一点静态可证：`lea ecx,[edx+0x78]`）。
`+0xb8` 可能是通道类型/上限枚举。

---

## 5. 令牌桶配对规律（用户三份数据都一样）

```
0x54b4888 (524288000, n=125)  ↔  0x54b48b8 (16384, n=125)
0x7f542c0 (524288000, n=127)  ↔  0x7f542f0 (16384, n=127)
0x54b4210 (524288000, n=98)   ↔  0x54b4240 (16384, n=98)
```

配对出现，consume 次数**完全一致**，`set` 次数不同（大桶 1 次 / 小桶 12~20 次）。
连地址都只差 0x30 —— 同一个对象里的**相邻两个字段**。

→ 这是**同一个通道的上行/下行**（或字节/请求）两个桶。
小桶停在 16384 说明"这一方向没有被设速率"，**不是限速证据**。
上一版把它们当"瓶颈"是错的。

---

## 6. 那么瓶颈在哪？—— 三个候选，按优先级

### 候选 1：在 netbase.dll（网络层），不在 kernel.dll ✅ 最可能

- kernel.dll 静态导入 `WS2_32.dll`（`WSARecv`/`WSASend`/`WSAIoctl`/`WSAEventSelect`）
  和 `MSWSOCK.dll`（`AcceptEx`），**没有 netbase.dll 的导入**（`docs/08` 已确认）。
- 但 `probe.js` / `probe2.js` 的调用栈里**反复出现 `netbase.dll+0x...`**
  （`docs/11` 记录过被过滤掉的 non-kernel frame）。说明 netbase.dll 是独立的
  网络引擎，通过**回调/函数指针**跟 kernel.dll 交互。
- 用户的桶计数在 boost 后持续增长（19→61→67）→ 连接在不停新建/重连。
  **这非常像 netbase 侧在按自己的节奏建连、限并发。**

### 候选 2：非令牌桶的固定 sleep / 定时器

`consume` 的所有 1372 次调用只来自**一个**调用点 `0xdd15e`（`0xdd150` 函数体内），
说明令牌扣减路径是单线的。如果 netbase 侧按固定间隔喂数据，再怎么放开桶也没用。

### 候选 3：服务端侧（CDN/peer 给的带宽）

`docs/02` 记录过服务端下发 `max_speed`。用户账号若是非会员，
服务端可能直接按 120 KiB/s 发数据 —— 客户端放开也没数据可下。
这一点客户端改不了。

---

## 7. 新增的观测手段：黑洞检测（第 4.5 节）

`probe2.js` 现在多了一节 4.5「黑洞检测：令牌被谁吃掉了」，判据是：

1. **抽干率** = `consume` 调用时"余额 < cap/2"的比例。抽干率高 = 这个桶一直在等令牌 = 它才是瓶颈。
2. **实测补充速率** = 两次调用之间令牌涨了多少 / 间隔。跟 `rate` 字段对比：
   - 实测补充 ≈ rate → 桶工作正常
   - 实测补充 ≪ rate（而 rate 已经很大）→ **补充函数被别处压住了**，rate 只是标称值
3. **`consume` 合计 vs 抽干次数**：如果全部 `consume` 里抽干比例都很低，
   那就是"令牌够用、数据没来" → 瓶颈明确在 kernel.dll 之外。

这一节能直接排除/确认候选 2。

---

## 8. 下一步：把 hook 挂到 netbase.dll 上

用户 `probe.js` 的栈里已经有 netbase 的帧。下一步要做的是：

1. `Process.enumerateModules()` 打印 netbase.dll 的 base/size/导出
2. 在**用户态网络 API** 上挂点：`ws2_32!WSARecv` / `ws2_32!WSASend`（导出符号，不用猜 RVA），
   统计**实际收发字节数**和**调用频率**
3. 用 `setInterval` 每 2 秒采样累计字节 → 得到**实测吞吐曲线**
4. 把吞吐曲线和各桶的 `consume` 速率对时间对齐：
   - 吞吐 ≈ 桶配额 → 桶有效
   - 吞吐 ≪ 桶配额 → 确认"数据没来"，去 netbase 侧找限速

第 2 步不需要任何 RVA，是导出函数，**不会重演"猜地址"的错误**。
