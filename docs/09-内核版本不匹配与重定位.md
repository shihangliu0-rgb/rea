# 09 · 内核版本不匹配：为什么 13 个点位全部"字节不匹配"

> 现象（用户实测，`baidunetdiskhost.exe` pid=27568）：
> ```
> [!] 跳过 set_param：RVA 0x1225f0 处字节不匹配 期望=55 89 e5 53 57 56 83 ec 2c 实际=50 e8 ca 3c fb ff 83 c4 04
> …… 13 条全部不匹配 ……
> ========== 安装完成：成功 0 个，跳过 13 个 ==========
> ```
> 这说明**脚本没写错、hook 机制没问题**，而是**它们指向的是另一个版本的 kernel.dll**。

---

## 1. 先给结论（三条实测证据）

| 证据 | hooks.js 的目标 | 你的机器 |
|---|---|---|
| `SizeOfImage` | **0x2a3a000 = 42.23 MB** | **43.1 MB**（census.py 报） |
| 加载它的进程 | 8.1.6.101 的 `BaiduNetdisk.exe` | **`baidunetdiskhost.exe`** |
| 加载基址 | 样本按 `0x10000000` 设计 | 实际 **0x78100000**（ASLR，正常，无影响） |

**`SizeOfImage` 不一样，就意味着整个 `.text` 节的长度不同 → 每个函数的 RVA 都变了。**
42.23MB 和 43.1MB 差约 **0.87MB 代码**，不可能只是编译差异。

`base = 0x78100000` 不是问题（DLL 默认就带 ASLR，`hooks.js` 里所有 hook 都是
`base + RVA` 算出来的，不看固定基址）。

另外两个细节，说明你这套客户端比本仓库分析的版本**更新**：

- 你的进程列表里出现了 **`BaiduNetdiskUnite.exe`（9 个）** 和 **`baidunetdiskhost.exe`（3 个）**。
  在本仓库的 `BaiduNetdisk.exe` 里，`BaiduNetdiskUnite.exe` 只出现在
  `'module\\BrowserEngine\\BaiduNetdiskUnite.exe'` 这一条路径里，`baidunetdiskhost` **完全搜不到**。
  → 你装的是**架构更新的一版**（Chromium 内核的壳 + 独立下载宿主进程）。
- 你的 `kernel.dll` 比样本**大 0.87MB**。

---

## 2. 为什么"13 个全错"反而是好消息

`hooks.js` 每挂一个点之前都会**先读 5 个字节比对签名**，不对就跳过（不 attach）。
这个设计现在正好起作用了：如果它硬挂，13 个点会全部插在指令中间，
客户端**会当场崩**（而且大概率是在你已经开始下载的时候崩，损失更大）。

所以你看到 13 条"跳过"，等价于：

> **这 13 个 RVA 在你的版本上一个都不成立，一个字节都没改你的进程。**

---

## 3. 三个可选路线（按推荐顺序）

### 路线 A（推荐）：离线重定位 —— 拿到那个 43.1MB 的 `kernel.dll`

```bat
REM 1. 找到它
dir /s /b "D:\Wang_Pan\BaiduNetdisk\kernel.dll"
REM    或者在任务管理器里右键 baidunetdiskhost.exe -> 打开文件所在位置

REM 2. 离线扫描（不用 hook，不会崩）
python re\frida\rescan.py --dll "D:\Wang_Pan\BaiduNetdisk\kernel.dll"
```

`rescan.py` 会打印：

```
版本信息：FileVersion=?.?.?.?  SizeOfImage=0x??????? (43.1MB)
  ⚠ 与 hooks.js 的目标版本 3.0.20.237 不同 → RVA 需全部重新定位

点位                           旧RVA       新RVA       候选     命中方式
set_param                    0x1225f0   0x??????   ...
```

⚠ **注意**：`rescan.py` 现在用的是**短签名**（5 字节以内）做锚点。
43.1MB 版本里这些短序列会命中几十处，脚本会按"离旧 RVA 最近"排序，
但这只是**启发式**，必须再用 `verify_rva.py --add` 逐条确认，
或者用路线 B 在活体进程里交叉验证。**不要直接拿去 hook。**

### 路线 B：活体进程里扫（不用拷文件，最快）

```bat
python re\frida\locate.py --pid 27568
```

它在运行中的 `kernel.dll` 内存镜像里扫同样的特征，直接给出 RVA 候选，
最后打印一段**可直接粘进 `hooks.js`** 的 `PROFILES` 条目：

```
把下面这段粘进 hooks.js 的 PROFILES，并把 PROFILE 改成这个 key：
    'size_0x2b10000': {
        note: '自动生成，SizeOfImage=0x2b10000 (43.10MB)',
        'set_param': 0x??????,   // 3 个候选，请人工确认
        ...
    }
```

同理：候选数 >1 的点必须人工确认。

### 路线 C（最省事、最可靠）：换回 8.1.6.101

本仓库所有报告（docs 01–07）、`hooks.js` 的 13 个点位、`bin/kernel.dll`
（3.0.20.237）都是**同一份**。要复现报告里的结论，用同版本客户端最省成本：

1. 卸载当前版本
2. 装 8.1.6.101（安装包自备）
3. 直奔 `hooks.js` 那 13 个 RVA —— `verify_rva.py` 会给你 `OK=13 BAD=0`

> 这条路的好处：`docs/06`（变速反噬）、`docs/07`（SVIP 试用）里的每一个地址
> 都是在这个版本上验证过的，换成新版本需要把 01–07 全部重做一遍才严谨。

## 4. `hooks.js` 已经为多版本做好准备

这次改造后，`hooks.js` 不再把 RVA 写死在 hook 调用里，而是：

```js
var PROFILE = '3.0.20.237';        // ← 你只要改这一行

var PROFILES = {
    '3.0.20.237': { note: '8.1.6.101，SizeOfImage=0x2a3a000 (42.23MB)',
                    'set_param': 0x1225f0, ... },
    // 'size_0x2b10000': { ... }   ← locate.py 生成的条目粘在这里
};
```

启动时会做**版本指纹**检查：

```
[+] 版本核对通过：SizeOfImage = 0x2a3a000 (42.23MB)
```

或者：

```
!!!!!! 版本不匹配 !!!!!!
  本脚本的 RVA 定在 kernel.dll 3.0.20.237 上（8.1.6.101）
  期望 SizeOfImage = 0x2a3a000  (42.23MB)
  实际 SizeOfImage = 0x2b10000  (43.10MB)
  → 13 个 RVA 全部错位，逐个报"字节不匹配"就是这个原因。
  → 不要硬挂，会插到指令中间导致崩溃。正确做法：
     A. 离线重新定位： python rescan.py --dll "<安装目录>\kernel.dll"
     B. 换回 8.1.6.101 的 kernel.dll 再分析
```

这样下次换版本，**第一行输出**就告诉你原因，不用等 13 条"跳过"。

## 5. 顺带修掉的另一个误判

之前 `hooks.js` 的诊断里说"kernel.dll 是点下载才加载"。你这台机器上的事实是：

- `census.py` 扫的时候客户端**正在下载**，`kernel.dll` 在 **`baidunetdiskhost.exe`** 里 ——
  不是主 UI 进程 `BaiduNetdisk.exe`（那个只有 141 个模块，**没有** `kernel.dll`）
- 主进程 `BaiduNetdisk.exe` 只有 `YunDls.dll` / `YunLogic.dll`（无 `netbase.dll`）
- 下载宿主 `baidunetdiskhost.exe` 有 `kernel.dll` + `netbase.dll`

→ **结论：下载内核跑在独立的宿主进程里。** 以后 attach 要认进程名
（`census.py` 会自动告诉你哪个）。

## 6. 交付物

| 文件 | 作用 |
|---|---|
| `re/frida/rescan.py` | 离线（静态 PE）重定位，读 FileVersion / SizeOfImage 做版本指纹 |
| `re/frida/locate.py` | 活体进程内 `Memory.scanSync` 重定位，直接输出可粘贴的 PROFILES 条目 |
| `re/frida/census.py` | 多进程模块普查（找出哪个 pid 有 kernel.dll） |
| `re/frida/verify_rva.py` | 离线核对某一版 RVA（支持 `--profile`、`--add`） |
| `re/frida/hooks.js` | 版本指纹 + `PROFILES` 多表 + 幂等安装 |
| `re/frida/tests/smoke.py` | 提交前自检：node --check + 假 Frida API 实跑 agent + verify_rva 正负例 |

### 附：`locate.py` 第一次跑报 `ReferenceError: 'kernel' is not defined`

原因是注入模板里 `var modName = %s;` 用 `%` 拼字符串，`'kernel.dll'` 的引号被吃掉，
生成出来是 `var modName = kernel.dll;`。已改成 `json.dumps()` 注入，并加了
"生成后先 `node --check`" + 假 Frida API 实跑的回归测试（`tests/smoke.py`）。
顺手修掉的还有：`Memory.scanSync` 找不到时指针不前进会死循环（现在有 `stuck` 防御）、
`--limit` 只取前 8 个命中导致真正候选被漏掉（现在收集 400 个再筛）、
脚本报错时仍傻等 90 秒（现在立刻返回）。

## 7. 第二轮实测：`locate.py` 全 0 命中（"扫描被拒绝"）

用户输出：

```
set_param                    旧=0x1225f0   命中=0  (扫描被拒绝)
…… 12 条全部 命中=0 (扫描被拒绝) ……
```

### 7.1 先分清两件事

| 提示 | 含义 |
|---|---|
| `命中=0  ✗ 这条特征在这个版本里确实没了` | 扫描成功，但短签名真的匹配不上（版本差异大） |
| `命中=0  (扫描被拒绝)` | **`Memory.scanSync` 自己抛异常了**，一个字节都没扫 |

第二轮全部是后者 → **不是"特征没了"，是扫描根本没有发生**。

### 7.2 根因：一次扫 43MB

`locate.py` 之前是 `Memory.scanSync(base, modSize, pat)` —— 一次性把整个 43MB
交给 Frida。Frida 对单个 range 有上限，超出直接抛 `invalid argument`，
被 `catch` 吃掉 → 每条都变成"扫描被拒绝"。

已修：改成 **64KB 一页循环扫**（`PAGE = 0x10000`），逐页 try/catch，
并统计 `refuse`（被拒页数）/ `pages`（总页数）。现在会打印：

```
set_param                    旧=0x1225f0 命中=3
                               ✗ 可读区里没命中        ← 扫过了，真没有
update_max_speed             旧=0x2dd200 命中=0  ⚠ 2/673 页读不了   ← 部分页有问题
```

如果**所有页都被拒**（`refuse == pages`），会打印一段结论并建议走离线路线：

```
!!!!!!...
扫描基本全被拒绝（673 次）—— 这不是「特征没了」，是脚本读不了这块内存。
  1) 这个 kernel.dll 被保护（VMProtect/Themida/页属性 PGUARD）
  2) 客户端是 32 位但宿主进程有反注入
  3) 权限不足 —— 用管理员身份运行 cmd 再试
下一步：换**离线**路线，不碰进程：
  python rescan.py --dll "D:\Wang_Pan\BaiduNetdisk\kernel.dll"
```

### 7.3 为什么离线路线更可靠

`rescan.py` 直接读文件字节，**完全不依赖 Frida、不依赖内存权限、不依赖进程保护**。
你这个版本 SizeOfImage = `0x2b25000`（43.14MB），文件就在
`D:\Wang_Pan\BaiduNetdisk\kernel.dll`（`locate.py` 的 head 输出里给了完整路径）。

```bat
python rescan.py --dll "D:\Wang_Pan\BaiduNetdisk\kernel.dll"
```

### 7.4 回归测试

`re/frida/tests/harness_locate.js` 现在**故意让 `Memory.scanSync` 在大 range 时抛异常**，
模拟真机行为；如果分页逻辑失效，测试会直接失败（`refused > 0` → HARNESS FAIL）。
这样"整段扫 → 全被拒"这类问题以后不会再被漏过。
