# 01 · 总览：这份报告回答什么

## 0. 一句话结论

> **限速不在服务器上"掐"你的带宽，而是在 `kernel.dll`（百度 P2P SDK 3.0.20.237）里由一个"令牌桶 + 目标速度抖动"的模块主动把下载速率压到一个由服务端下发参数算出来的值。**
> 服务端只给"参数"（`basic_speed` / `UserSpeedLimit.total_s` / `p2s_s` / 会员标记 / 各级连接数），
> 客户端自己算出 `target_speed`，再由每个 peer 的令牌桶按字节数放行。
> 下载速度则 = `拿到的可用链路数 × 每链路允许速率`，两个因子分别被两份不同的代码控制。

三段对应关系（详细内容见 02 / 04 篇）：

| 你感觉到的现象 | 真正的机制 | 代码位置（RVA，kernel.dll） |
|---|---|---|
| 非会员固定在 ~120 KiB/s | 服务端 `p2p_switch_param.basic_speed=122880` → 客户端 `download_total_speed_default=122880` 作为 `max_speed` 基座 | 配置加载 `0x2e43a0`；计算 `0x2ddb90` |
| 速率一直在小幅波动，不是一条直线 | `calculate_target_speed` 每次采样在 `[restrict_ratio, 100%]` 之间**随机抖动**，再乘 `max_speed` | `0x2ddb90`（抖动表 `0x1119e4d4` / 符号表 `0x1119e4fc`） |
| 会员能跑满，但"看着快、实际被限" | `UserSpeedLimit={"p2s_s","total_s"}` 直接写进限速器；`TryVipToken` 决定"是否允许提速" | `set_user_speed_limit` @`0xb4b84`；`set_vip_try_token` @`0x20c530` |
| 任务多、连接多也没更快 | 连接数是**按"网络等级"给定的表**（level1/2/3 = 4/2/1），不是越多越好 | `0x2e43a0` 末段 → `set_subbit_count` @`0xb8430`/`0xb8480` |
| 大文件才开始用 P2P、小文件走 CDN | 阈值 `download_file_p2p_size=524288000`、`min_p2p_download_file_size=5242880` | `YunLogic.dll` 内嵌配置（见 02 篇附表） |
| "CDN 被关掉后就慢了" | `close cdn` 决策：P2P 速度不足以满足 `level` 对应阈值时，主动关闭 CDN/onecloud 链路 | `0x1aea38`（核心块 `0x1aeadc`） |

## 2. 分析路线（可复现）

1. **静态打底**：`pefile` 提段表/导出/导入/PDB 路径 → `re/tools/dump_all.py`
2. **字符串语料**：全量 ASCII 抽取 → `re/tools/extract_strings.py`（18 MB）
3. **交叉引用**：`re/tools/kb.py`（RVA↔偏移、字符串 xref、`callers()`、`jmp_slots()`）
4. **★ 反推符号表**：MVSC 日志宏把 `{type, file, func, line}` 写进栈帧，代码里表现为
   `mov [eax+0x1c], "函数名"` + `mov [eax+0x20], 行号`；把这两条指令配对就能批量还原函数名。
   → `re/tools/logsites.py` + `re/tools/funcmap.py`，**从 0 个符号恢复到 1531 个函数名（719 个唯一函数名）**，
   产物 `re/out/funcmap_kernel.dll.csv`。这一步是本次逆向效率的关键，后面所有"`start_speed_control` / `calculate_target_speed` / `cdn_speed_limit_dispatch`"
   这类名字都是这么来的，不是猜的。
5. **日志实证**：解 XOR 后拿到服务端真实下发值 + 本地真实行为（`TryVipToken`、`UserSpeedLimit`、`key=8/37` 的参数注入顺序）。
6. **动态验证点**：`re/frida/` 里给了 8 个可直接下的 hook 点和参数偏移。
