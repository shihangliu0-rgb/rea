# 04 · 下载速度的全链路逻辑

> 把"点一下下载"到"数据落盘"拆成 7 个阶段，每阶段给出：做什么 → 谁做的（RVA）→ 证据。
> 符号来自 `re/out/funcmap_kernel.dll.csv`；函数名后的 `(L123)` 是该函数日志点所在源码行号，
> 因此**行号也构成了"同一个 .cpp 文件里函数先后顺序"的线索**（见 §7 的源文件还原）。

---

## 0. 全景

```
用户点下载
   │
   ├─[A] 建任务        create_task / start_task         0x100e9f28… 0x10303b90
   │      └─ 判定 P2P 还是纯 CDN（按文件大小阈值）
   │
   ├─[B] 取链          CMS config → locate_download     0x6d627e(handle_response)
   │      └─ 拿 dlink / bakurls / antdown=ssl / is_encrypt
   │
   ├─[C] 造 peer        generate_http_peer_node_from_url 0x101f355f
   │      └─ announce_http_peer / announce_normal_peer  0x101fef80 / 0x101f8aa4
   │
   ├─[D] 连 peer        connect_http_peer / connect_normal_peer 0x10216e72 / 0x10218094
   │      └─ 按 level 上限算连接数 add_success_peer      0x1021bcf0
   │
   ├─[E] 分片调度       choose_peer / request → piece   0x101a0e88
   │      └─ 慢 peer 剔除 filter_slower_p2p_peer
   │
   ├─[F] 速度闸门       ★ SpeedLimitor.calculate_target_speed 0x2ddb90
   │      └─ ★ AccumulateTokenBucket.consume  0x2db170   ← 真正掐速率
   │
   └─[G] 上报/反馈      report_download_common 0x2f667e / cdn_speed_limit_dispatch 0x2ed84e
          └─ 服务端据此调整下一轮参数（闭环）
```

**核心答案：下载速度 = min(链路数 × 每链路有效速率, 令牌桶配额)。**
- 前一项被"连接数策略（level 表）+ 文件大小阈值 + peer 质量"限制；
- 后一项被"服务端参数 → `calculate_target_speed`"限制。

```asm
call  0x103063f0            ; 取 task 对象
test  ecx, ecx
je    err_start_task        ; 日志 "|err start task|id=%1%|task_handle=%2%|"
mov   eax, [ecx] ; call [eax+0x3c]   ; vtable: task->status()

```

→ 存在"**包下载（package download）**"这一独立路径（`use_package_download_ver_2`、`max_pkg_download_count`），
它走的是"先下整包再拆"的模式，速率模型与普通任务不同。🟡（代码里只有日志与开关，未追到具体限速点）

**P2P vs 纯 CDN 的判定**（配置驱动）：

```
if (filesize < min_p2p_download_file_size)       → 只走 CDN（http peer）
if (filesize > download_file_p2p_size)           → 允许 P2P + CDN 混合
if (seeder_count < downloader_count * 4)         → P2P 降级
if (seeder_count < p2p_seeder_minmum(500))       → P2P 降级
```

### 5.2 速度闸门（02 篇 §4/§5 的实现细节在此处生效）

```
choose_peer() → insert_request_to_peer()
                       ↓
             需要发 request 前问一次桶:
             AccumulateTokenBucket::consume()   @0x2db170
                       ↓ 返回可用字节
             0 → 本 tick 不发 request（peer 空闲）
             n → 发 request(len = min(n, block_size))
```

**这就是"限速"的物理位置：不是限制 socket 带宽，而是"少发 request"。**
因为 BT/HTTP 分片下载是"请求驱动"的，request 少了对端自然发得少。
优点：省内存、省流控复杂度；缺点：**可以靠改 `rate` 字段/打 patch 直接解限**。

### 5.3 `close cdn`：把"慢"变成"更慢"的负反馈

函数入口 `0x1aea38`（核心块 `0x1aeadc`；`re/out/f_1ae_head.txt` + `f_1aeadc.txt` 有完整反汇编）。
它由 `old_cdn_close_strategy` @`0x1ae607`(L928) 这条策略链调用。

```c
// 入参: level = [ebp-0xec]   (来自 edi+0x20 的速度/等级判定)
int  base;         // [ebp-0xd8]  阈值
int  cdn_speed;    // [ebp-0xd4]  允许的 cdn 速度, 默认 0x100000
base = 0x10; cdn_speed = 0x100000;                  // 缺省: 阈值 16, 速度 1 MiB/s
if (level >= 1 && level <= 5) {                      // cmp edx,4 / ja
    double d = (double)level;                        // movd xmm0,ecx + por (见下)
    d = 9.0 - d;                                     // subsd [0x1119b770]=9.0
    d = d * 0.25;                                    // mulsd [0x1119b778]=0.25
    d = d * 1024.0 * 1024.0;                         // mulsd 两次 1024.0
    cdn_speed = (int)d;                              // cvttsd2si + 溢出面处理
    base = 0x20 - level * 4;                         // lea edi,[ecx*4]; esi=0x20-edi
}
if (speed_measured([edi+0x20]) < level * base)       // cmp [edi+0x20], ecx / jae
    if (accumulated < base || rate < cdn_speed)      // 两个 jb 到 0x1af9e2
        → 走"关闭 CDN/onecloud 链路"分支
```

数值示例（`level` → `cdn_speed` 阈值 / `base`）：

| level | cdn_speed 阈值 | base | 备注 |
|---|---|---|---|
| 1 | (9−1)×0.25×1 MiB = **2 MiB/s** | 28 | |
| 2 | **1.75 MiB/s** | 24 | |
| 3 | **1.5 MiB/s** | 20 | |
| 4 | **1.25 MiB/s** | 16 | |
| 5 | **1 MiB/s** | 12 | |
| 其它 | 1 MiB/s（缺省） | 16 | |

触发时打的日志（字面量 `0x11288efd`，`push` 在 `0x1aeba8`）：

```
close cdn|p2p_speed=%1%|onecloud_speed=%2%|onecloud_http_speed=%3%|p2p_ct=%4%|
onecloud_ct=%5%|onecloud_http_ct=%6%|threshold_non_cdn_ct=%7%|
threshold_non_cdn_rate=%8%|downloading_task=%9%|global_peer_ct=%10%|...
```

> ⚠️ 反汇编里 `movd xmm0, ecx ; por xmm0, [0x1119b760]` 看着像"位运算脏技巧"，
> **实际是编译器的 double↔int 转换惯用法**：`[0x1119b760]` = `4503599627370496.0` = `2^52`（掩码常量），
> 用它把整数无分支转成 double。所以这段就是标准的 `(double)int` 转换，语义干净。
> 常量表实测：`0x1119b770=9.0`、`0x1119b778=0.25`、`0x1119b780=1024.0`、`0x1119b788=2^31`。

**业务含义**：CDN 链路（IDC/onecloud/pop）本来是最快的通道。当"实测速度 < level 阈值"时，
客户端**主动砍掉 CDN 链路**，只留 P2P —— 于是速度更难恢复，形成"越慢越关、越关越慢"的负反馈。
这是"非会员下载体验差"的关键一环。✅（有完整算式 + 日志文案双重证据）

## 8. 一图看懂"为什么慢"

```
                    ┌── 文件太小 (<5MB) ────────────→ 只有 CDN
                    │
 任务建立 ──→ 通道选择 ├── 没有 seeder/被限 ───────────→ 只有 CDN/直连
                    │
                    └── 正常 ──→ P2P + CDN
                                   │
      CDN 被 close cdn 砍掉 ←──────┤（速度 < level 阈值时）
                                   ↓
      连接数 = level 表(4/2/1) ──→ 同时并发的链路就这么几个
                                   ↓
      每链路速率 = 令牌桶 rate ──→ 桶里没令牌就不发 request
                                   ↓
      总速率上限 = max_speed × (restrict_ratio + 抖动)%   ← 服务端给 max_speed
                                   ↓
                              ≈ 120 KB/s（非会员）
```
