# 12 — 限速决策器定位成功：`0x19fab0` 与 `+0xb0`

> 承接 [11-242点位复核与调用栈追踪](./11-242点位复核与调用栈追踪.md)。
> 本文结论全部来自**用户真机 `probe2.js` 的运行时调用栈** + **本地样本反汇编**互证。
> 每一个运行时栈帧的返回地址，都能在静态反汇编里精确对上一条 `E8` 调用指令。

---

## 1. 一句话结论

**真正决定"限制到多少"的是 `kernel.dll+0x19fab0` 这个虚函数。**
它读自己对象上的 **`+0xb0`（限速值，字节/秒）** 和 **`+0xb4`（限流开关）**，
然后调用 `TokenBucket::set_rate()`。

```
0x19fae2  cmp  dword ptr [edx + 0xb4], 0     ← 限流开关
0x19fae9  je   0x19fce3
   ...（开关打开时：先走一遍其它逻辑）
0x19fce3  lea  ecx, [edx + 0x78]              ← 内嵌的 TokenBucket
0x19fce6  push dword ptr [edx + 0xb0]         ← 限速值
0x19fcec  call TokenBucket::set_rate  (0x100dd320)
```

它**没有任何 `E8` 直接调用者** → 它是**虚函数**，只能通过 vtable 调。
这就是之前"静态 xref 追不到上游"的根本原因：**上一版只扫 `E8`，漏了 `call [reg+off]`。**

---

## 2. 运行时证据（用户 probe2.js 实测，逐字）

```
set_rate 共 119 次，consume 共 1385 次
线程：1 个调用过 set_rate
```

调用者排行第 1 名、也是 43 次 `16384` 的唯一来源：

```
0x19fcf1   56 次  47.1%
    这个调用者下发过的全部速率：
        16384×43, 122880×7, 21488×2, 27185×2, 36733×1
```

它的完整调用链：

```
#0 kernel.dll+0x19fcf1   ← set_rate 的返回地址 = 0x19fcec 那条 call
#1 kernel.dll+0x2fc866   ← call [edx+0x28]（虚调用，所以静态追不到）
#2 kernel.dll+0x2551b6   （另一条路径是 0x2f0b24 → 0x1dad8d → 0xa0b0c）
#3 kernel.dll+0x310a23
#4 kernel.dll+0xf83f3
#5 kernel.dll+0x101f0c
#6 kernel.dll+0xd087
#7 kernel.dll+0xcb08
#8 kernel.dll+0x696e
#9 kernel.dll+0x3d5bf4
```

`#1 → #0` 这一段静态可证：

```
0x2fc851  mov ecx, [esi+8]
0x2fc854  mov edx, [ecx]
0x2fc856  mov edx, [edx+0x28]      ← 从 vtable 取方法
0x2fc863  push eax
0x2fc864  call edx                 ← 虚调用 → 0x19fab0
```

## 3. 一个必须记住的新事实：调用链会变

| 场景 | 第 5 层 frame |
|---|---|
| 用户看 `why(16384)` 时 | `0x19fcf1 → 0x2fc866 → 0x310b3e → 0xf83f3` |
| 用户看 `report()` 时（同一台机、同一进程） | `0x19fcf1 → 0x257839 → 0x2551b6 → 0x310a23 → 0xf83f3` |

同一进程里两次采样，中间层就换了一条路。**所以"链路指纹"不能写死**，
定位要落到"函数 + 字段"上（这里是 `0x19fab0` + `+0xb0`），而不是落到某条链上。

## 4. 令牌桶：25 个，谁是瓶颈

用户实测（前 10 个，按 consume 次数排）：

| 桶地址 | rate | cap | set 次数 | consume 次数 | 最后一次 set 来自 |
|---|---|---|---|---|---|
| `0x795b3918` | 122880 | 122880 | 7 | **629** | `0xe45af` |
| `0xc63e050` | 524288000 | 524288000 | 1 | **298** | `0x1915eb` |
| `0x8221ee8` | 524288000 | 524288000 | 1 | **198** | `0x1915eb` |
| `0x82229b0` | 524288000 | 524288000 | 1 | 35 | `0x1915eb` |
| `0x82229e0` | **16384** | **16384** | 11 | 35 | `0x19fcf1` |
| `0x81927b8` | 524288000 | 524288000 | 1 | 34 | `0x1915eb` |
| `0x81927e8` | **16384** | **16384** | 10 | 34 | `0x19fcf1` |
| `0x7fd14a0` | 524288000 | 524288000 | 1 | 32 | `0x1915eb` |
| `0x7fd14d0` | **16384** | **16384** | 8 | 32 | `0x19fcf1` |
| `0x7fd0c00` | 524288000 | 524288000 | 1 | 24 | `0x1915eb` |

观察：

1. **每个"大桶"后面都紧跟一个 `16384` 的小桶**（`0x82229b0`/`0x82229e0`、
   `0x81927b8`/`0x81927e8`、`0x7fd14a0`/`0x7fd14d0`）。配对出现，consume 次数几乎一样。
   最可能的解释是**同一通道的上行/下行两个方向**，或者**请求数与字节数两个维度**。
   🟡 这个还没证实。
2. **`consume` 次数最高的桶是 `0x795b3918`，rate 只有 122880**，629 次 consume。
   这是最像"主通道限速"的一个。
3. `524288000` 的桶 consume 次数也不低（298/198），rate 是哨兵值 = 不限。
   **"不限"的桶 consume 次数高，说明频率不是瓶颈，字节数才是。**

## 5. `+0xb0` 的值从哪来？——静态查不到，这是结论不是借口

在整个 45 MB 文件里扫"写 `[reg+0xb0]` 的立即数"：

| 立即数 | 写入 `+0xb0` 的次数 |
|---|---|
| 16384 (`0x4000`) | **0** |
| 122880 (`0x1E000`) | **0** |
| 1006860 | **0** |
| 524288000 | **0** |
| 104857600 | **0** |

**一次都没有。** 说明 `+0xb0` 是运行时算出来的（服务端下发 × 会员系数 × 限速比例），
不是代码里的常量。这跟 `docs/02` 的机制结论一致，但现在有了确切的落点。

所以想提速，**必须写 `+0xb0`（或直接写桶），不能靠打补丁改某个常量**。

---

## 6. `boost()` 现在做三件事

`probe2.js` 里的 `boost()`（默认关，敲了才生效，**不会重新 attach**）：

1. **限速器 `0x19fab0` 每次进入前**，把 `this+0xb0` 写成 `0x1F400000`（524288000 B/s）
2. **`set_rate` 的入参**换成 `0x1F400000`
3. **每次 `consume` 之前**，把桶的 `+0x20`(rate) / `+8`(cap) 再写一遍

🟡 **尚未在真机验证实际效果。** 验证方法：`boost()` → 重新点下载 → 看速度 +
30 秒后 `report()`。判读方式：

| 现象 | 含义 |
|---|---|
| 速度上去了 | 令牌桶就是瓶颈，收工 |
| rate 已经 524288000 但速度不变，`consume` 次数也不变 | 瓶颈在"每 tick 请求数"，不在桶 |
| rate 已经 524288000 但一下子又变回 16384 | 还有一处在我没 hook 的路径上写 `+0xb0`，下一轮去抓 |

## 7. 已公证的 242 点位（可直接用）

| 名称 | RVA | 类型 | 签名（唯一匹配数） |
|---|---|---|---|
| 限速器 `apply_limit` | `0x19fab0` | 虚函数 | `55 89 e5 53 57 56 81 ec cc 00 00 00`（2 处） |
| 限流开关 `set_limit_enabled` | `0x19fd30` | 虚函数 | `89 c8 8b 4c 24 04 89 88 b4 00 00 00`（**1 处**） |
| `set_x_b8` | `0x19fd70` | 虚函数 | `8b 44 24 04 89 81 b8 00 00 00 c2 04`（**1 处**） |
| `TokenBucket::set_rate` | `0xdd320` | 普通函数 | `8b 44 24 04 85 c0` |

> `0x2a3a000`（237）**没有**限速器表 —— 没有 237 样本就不猜地址。
> 这是上一版翻车的直接原因，不再犯。
